# TripTogether 代码审查标准与流程（Code Review Standard & Process）

> 适用范围：TripTogether 全栈（React 18 + TypeScript + Vite + Ant Design + Zustand + Leaflet / Express + TypeScript + TypeORM + PostgreSQL）
> 版本：v1.0 ｜ 维护者：研发组 ｜ 状态：待团队确认后执行

---

## 0. 为什么需要这份标准（现状诊断）

代码质量参差不齐，根因不是"人不行"，而是**没有质量关卡兜底**。梳理当前仓库现状：

| 能力 | 现状 | 后果 |
|------|------|------|
| ESLint / Prettier | 无（根目录无配置文件，client/server 也无） | 风格全靠自觉，低级错误进主干 |
| TypeScript strict | 未开启（`tsconfig` 默认宽松） | `any` 横行，类型安全形同虚设 |
| 单元测试 | 无任何测试框架（无 jest / vitest 配置） | 改动无回归保护，越改越心虚 |
| CI / CD | 无 `.github/workflows` | 错误靠人肉发现，合并即上线风险 |
| 提交规范 | 无 PR 模板、无 lint-staged | Review 上下文缺失，评审成本高 |

更具体地，我抽样阅读了真实代码，已经能直接指出几个**会被本标准要求卡住的硬伤**（详见第 8 节）。这说明：标准不是纸上谈兵，它要能对准我们真实的坑。

**核心原则**：工具链先兜底（机器能查的别让人查），人工评审聚焦"机器查不出的设计与安全判断"。

## 1. 角色与职责

| 角色 | 职责 | 谁担任 |
|------|------|--------|
| **Author（作者）** | 自审、写 PR 描述、按意见修改、回复每一条评论 | 提交代码的开发者 |
| **Reviewer（评审人）** | 按清单评审、给出 🔴/🟡/💭 的结论、确认修改到位 | 至少 1 人；核心/安全/支付模块 ≥ 2 人 |
| **Owner（终审人）** | 对合并决策负责，处理争议，把控架构方向 | 项目负责人（梁） |

小团队约定：互相 review，但**自己写的代码不能自己批准合并**（避免"自批自"）。安全、费用分账、鉴权相关改动**必须**有第二人评审。

---

## 2. 严重级别定义（评审人统一用语）

| 标记 | 级别 | 含义 | 合并门禁 |
|------|------|------|----------|
| 🔴 | **Blocker 必须改** | 安全漏洞、数据损坏/丢失、崩溃、破坏契约 | **不修不准合并** |
| 🟡 | **Should-fix 应该改** | 明显隐患、重要路径缺测试、性能/N+1、可读性差 | 必须回复：改 or 登记技术债（说明理由） |
| 💭 | **Nit 建议** | 命名、注释、次要风格、可选优化 | 可不改，但建议改 |

**评审结论三选一**：`Approved`（无 🔴 且无未决 🟡）｜`Changes requested`（存在 🔴 或必须处理的 🟡）｜`Comment`（仅 💭，可合并）。

## 3. 审查清单（按维度，贴栈）

### 3.1 安全（最高优先级，🔴 居多）
- [ ] **鉴权与授权**：任何读写接口是否校验"当前用户对该资源有权限"？（见第 8 节真实案例：`GET/PATCH/DELETE /:tripId` 缺授权）
- [ ] **不信任客户端身份**：禁止直接信任 `x-user-id` 之类的请求头作为用户身份（当前 `userContext` 即此问题，属 MVP 技术债，上线前必须替换为 token 校验）。
- [ ] **注入防护**：SQL 一律走 TypeORM 参数化 / `pg` 的 `$1 $2` 占位符，**禁止**字符串拼接 SQL。任何 `+` 拼 SQL 即 🔴。
- [ ] **输入校验**：对 `req.body` / `req.params` / `req.query` 做类型与范围校验（`amount`、`budgetTotal`、日期、分页参数）。`Number(amount)` 得到的 `NaN` 必须拦下。
- [ ] **错误信息**：不向客户端泄露堆栈/SQL 细节（统一错误中间件返回脱敏信息）。
- [ ] **敏感数据**：密码/密钥不落地日志；`User` 实体对外返回时剔除敏感字段。

### 3.2 正确性
- [ ] **错误处理**：每个 `async` 路由必须有 try/catch 或全局错误中间件兜底（当前所有路由都缺，DB 报错会抛未捕获异常 → 500 + 堆栈泄露，属 🔴）。
- [ ] **边界与空值**：数组越界、空数组（`participantIds.length === 0`）、`undefined`、除零（`perCapita` 分母为 0）等。
- [ ] **事务一致性**：跨多表写操作（创建 Trip + Member + Schedules）应包在 DB 事务里，失败可回滚。
- [ ] **并发/竞态**：共享状态、计数器、邀请码生成是否有冲突风险。

### 3.3 性能
- [ ] **N+1 查询**：列表接口避免循环内逐条查库（用 `relations` / `Promise.all` 批量，已在 `expenseRoutes` 用 `Promise.all`，点赞）。
- [ ] **全量加载**：`GET /` 是否拉了过多嵌套关联？考虑分页或投影。
- [ ] **前端渲染**：大列表（日程、成员）是否用 `key`、是否避免无意义重渲染；地图标注数据量过大时做聚合。

### 3.4 可维护性
- [ ] **类型安全**：禁止无理由 `as any`（当前 `(req as any).userId` 全量存在）；应 `declare module 'express'` 扩展 `Request` 类型。
- [ ] **命名**：变量/函数名表达意图；避免 `data1`、`tmp`、`handle2` 之类。
- [ ] **魔法值**：角色 `"owner"/"editor"`、状态 `"planning"`、邀请码长度 8 等提取为常量或枚举。
- [ ] **重复代码**：跨路由的排序逻辑（`schedules.sort` + `items.sort`）应抽成公共函数。
- [ ] **函数长度**：单函数明显超过 ~80 行考虑拆分。

### 3.5 测试（当前完全缺失，分阶段补齐）
- [ ] 关键路径有测试：认证、创建/加入 Trip、费用分账计算。
- [ ] 边界有测试：非法输入、空数据、并发加入同一邀请码。
- [ ] 前端：组件关键交互用 Vitest + Testing Library 覆盖。

### 3.6 前端专项（React / Ant Design / Zustand）
- [ ] **状态管理**：Zustand store 是否只放真正跨组件共享的状态；避免把服务端数据冗余进 store 造成双源真相。
- [ ] **Ant Design**：统一用 `Message`/`Modal` 反馈，不混用原生 `alert`；注意 `Form` 的校验规则。
- [ ] **API 层**：所有请求走 `src/api/client.ts` 统一封装；不散落 `axios.get`。
- [ ] **受控/非受控**：表单字段是否受控；`key` 稳定性；`useEffect` 依赖是否完整（避免无限渲染）。
- [ ] **地图（Leaflet）**：销毁时 `map.remove()` 防内存泄漏；中国地图瓦片生产环境需替换（已在技术选型中记录）。

### 3.7 后端专项（Express / TypeORM）
- [ ] **路由分层**：路由只做"解析请求 + 调 service + 返回"，业务逻辑下沉到 service 层（当前逻辑全堆在路由里，随业务增长会失控）。
- [ ] **统一响应**：成功/失败结构一致（`{ data }` / `{ error }`），HTTP 状态码语义正确（201 创建、204 删除、404 不存在）。
- [ ] **日志**：关键动作有结构化日志，便于排查；不记敏感字段。
- [ ] **配置**：密钥/连接串走环境变量（`.env`），不硬编码。

## 4. 端到端流程

见附图《TripTogether 代码审查流程》。文字版：

1. **开发自审**：本地跑 `lint` + `typecheck` + `test` 全绿；对照第 3 节清单自查；用 `git` 小步提交。
2. **提交 PR**：填 PR 模板（见第 6 节），说明"改了什么 / 为什么 / 怎么测的 / 影响范围"。
3. **CI 自动门禁**：`lint + typecheck + test + build` 任一不过 → 自动打回作者，禁止进入人工评审。
4. **人工评审**：
   - 至少 1 名 Reviewer；核心/安全/支付模块 ≥ 2 名。
   - 评审人按清单给 🔴/🟡/💭，每条都要说清"为什么"和"建议怎么改"。
   - 存在 🔴 → `Changes requested`，作者改完 re-request review。
   - 仅有 🟡/💭 → 可 `Approved`，未决 🟡 须登记技术债（见第 7 节）。
5. **批准合并**：Owner 终审；满足"≥1 批准 + 无未决 🔴 + CI 绿"方可合并。
6. **合并后收尾**：删除功能分支；补上评审中承诺的测试；把登记的 🟡 技术债转入 Issue 跟踪。

**SLA（建议）**：作者自审即时；Reviewer 在 PR 提出后 **1 个工作日内**给首轮反馈；紧急修复走"hotfix"标签可加速。

## 5. 工具链基线（先把地基补齐）

> 当前仓库**完全没有**这些配置。按第 7 节路线图先落地，否则标准无法自动执行。

### 5.1 依赖（client / server 各自安装对应项）
- **Lint**：`eslint` + `typescript-eslint` + `@typescript-eslint` 规则集
- **Format**：`prettier` + `eslint-config-prettier`（关闭与 prettier 冲突的规则）
- **TS 严格**：`tsconfig` 开启 `strict: true`、`noUncheckedIndexedAccess`、`noImplicitAny`
- **Test**：client 用 `vitest` + `@testing-library/react`；server 用 `vitest` + `supertest`
- **Git 钩子**：`husky` + `lint-staged`（提交前只对改动文件 lint/format）
- **CI**：GitHub Actions（见 5.4）

### 5.2 推荐 ESLint 关键规则（节选）
```jsonc
{
  "rules": {
    "@typescript-eslint/no-explicit-any": "warn",        // 逐步消灭 as any
    "@typescript-eslint/no-unused-vars": "error",
    "@typescript-eslint/explicit-function-return-type": "warn",
    "no-string-concatenation-in-sql": "error",           // 自定义/插件规则，禁拼 SQL
    "security/detect-object-injection": "warn"
  }
}
```

### 5.3 tsconfig 关键项
```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitAny": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

### 5.4 CI 工作流（`.github/workflows/ci.yml` 示例）
```yaml
name: CI
on: [pull_request]
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci && cd server && npm ci && cd ../client && npm ci
      - run: cd server && npx eslint . && npx tsc --noEmit && npx vitest run
      - run: cd client && npx eslint . && npx tsc --noEmit && npx vitest run
      - run: npm run build   # 两端 build 通过
```

## 7. 落地路线图（分阶段，别想一步到位）

**阶段 0 — 工具链就位（1~2 天）**
- 装 ESLint + Prettier + TS strict + Vitest + Husky + lint-staged；写 CI 工作流。
- 先对**新代码**强制，老代码暂不 blocking（避免一次性爆炸）。

**阶段 1 — 清关键债务（紧随阶段 0）**
- 修第 8 节列出的 🔴：接口授权、全局错误处理、身份校验。这是上线前硬指标。

**阶段 2 — 流程固化（持续）**
- PR 模板 + 评审 SLA 跑起来；每周回顾一次 🟡 技术债；每月抽查一次 review 质量。

**阶段 3 — 测试文化（持续）**
- 新功能必须带测试；老模块按风险优先级补（`expenseRoutes` 的分账计算逻辑优先）。

## 8. 本项目高优先级待办（基于真实代码抽样，第一波要修）

以下来自 `server/src` 实际代码，作为标准"为什么重要"的活样本，也作为技术债第一批：

| # | 位置 | 问题 | 级别 |
|---|------|------|------|
| 1 | `tripRoutes.ts:35` `GET /:tripId` | 任何人凭 trip id 即可读取完整计划，无成员/权限校验（BOLA，OWASP API #1） | 🔴 |
| 2 | `tripRoutes.ts:169` `PATCH /:tripId` | 无授权即可修改任意计划 | 🔴 |
| 3 | `tripRoutes.ts:198` `DELETE /:tripId` | 无授权即可删除任意计划；且未处理关联数据级联 | 🔴 |
| 4 | `middleware/userContext.ts:12` | 直接信任客户端 `x-user-id` 头作为身份，可伪造任意用户 | 🔴（MVP 债，上线前必须换 token） |
| 5 | 所有路由（如 `tripRoutes.ts:20`） | 无 try/catch，DB 异常抛未捕获错误 → 500 + 堆栈泄露 | 🔴 |
| 6 | `expenseRoutes.ts:45` `Number(amount)` | 非数字输入得 `NaN` 入库，无校验 | 🟡 |
| 7 | 全局 `(req as any).userId` | 绕过类型系统，应扩展 `Request` 类型 | 💭→🟡 |
| 8 | `tripRoutes.ts:54-58` 排序逻辑 | 多路由重复，应抽公共函数 | 💭 |
| 9 | `tripRoutes.ts:14` 邀请码长度 8 | 魔数，提取为常量 | 💭 |

> 注：TypeORM 的 `findOne({ where: { id } })` 是参数化的，当前未直接出现 SQL 注入；但标准仍禁止任何字符串拼接 SQL，因为 `pg` 原生驱动已在依赖中，后续手写 SQL 时极易踩坑。

## 9. 评审人沟通规范（语气）

- 对事不对人：说"这段在并发下可能重复扣减"，不说"你这代码写的什么"。
- 每条 🔴/🟡 都要给"为什么 + 建议怎么做"，最好贴修复示例。
- 发现写得好的地方，显式点名表扬（好代码值得被看见）。
- 争议由 Owner 拍板，不陷入无限来回。
