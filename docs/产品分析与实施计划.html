1.4 关键发现

  • 市场已被验证：Wanderlog拥有100万+用户、App Store 4.9分，证明协作旅游规划需求真实存在
  • 但市场高度碎片化：没有一款产品能同时做好"协作+规划+进度+地图"，用户通常需要2-3个App组合使用
  • 国内市场存在空白：携程等大厂聚焦AI生成+预订闭环，四海轻旅聚焦App端，国内没有一款Web优先的协作旅游规划产品
  • 用户核心痛点未被解决：群聊里讨论→Excel记录→地图标记→记账App分钱，信息散落在4-5个工具中
  • "进度追踪"是独特切入点：几乎所有竞品都聚焦于"行程内容"，而你的想法中"各个阶段是否已完成"的进度追踪是市场上的空白点
  • Web端是差异化机会：头部竞品几乎都是App优先，Web端体验普遍较差。对于"一起坐在电脑前规划"的场景，Web是更自然的形态

二、可行性分析

2.1 技术可行性 — 高

技术维度评估
前端React/Vue + 实时协作可基于WebSocket/Yjs，技术栈成熟
后端Node.js/Python均可，RESTful API + WebSocket，无特殊技术门槛
实时协作Yjs / ShareDB 等CRDT库已成熟，或用WebSocket+操作广播简化实现
地图集成腾讯地图/高德地图JS SDK，支持标记、路线、距离计算
数据存储PostgreSQL + Redis（缓存/会话），标准方案
部署Vercel/Cloudflare Pages（前端）+ 云函数/轻量服务器（后端），成本低
用户认证微信扫码登录 + 邀请链接/邀请码，降低注册门槛

结论：所有技术组件都有成熟的开源方案，无需自研底层能力。MVP可由1-2人在4-6周内完成。

2.2 市场可行性 — 中高

  • 需求真实：多人出游是高频场景（家庭游、朋友结伴、公司团建），规划阶段的协作痛点普遍存在
  • 国内竞争格局有利：大厂（携程/飞猪）聚焦交易闭环，小厂聚焦单点功能，协作旅游规划的"进度管理+地图可视化"组合无人占据
  • 用户获取成本低：旅游规划天然有社交传播属性——邀请旅伴即拉新，病毒系数K>1的潜力大
  • 风险点：用户习惯用微信群+Excel解决，需要产品体验明显优于"DIY方案"才能促使用户迁移

2.3 商业可行性 — 中

变现模式可行性
免费 + 高级订阅（Pro）参照Wanderlog模式，免费版含核心协作功能，Pro版提供地图导出、离线访问、AI规划等
旅游产品佣金接入携程/飞猪/Booking联盟，用户在规划中点击预订获取佣金（中长期）
广告/品牌合作目的地旅游局、酒店品牌植入（远期）
API/白标为旅行社、企业团建提供白标版本（远期）

建议：MVP阶段完全免费，先验证用户留存和传播。日活达到一定规模后再引入Pro订阅和佣金分成。

总体可行性评估：推荐推进

技术可行性高，市场存在明确空白，商业模型有成熟参照。核心风险在于用户迁移成本（从微信群+Excel迁移到新平台），需要通过"邀请链接免注册查看行程"等机制降低门槛。建议以Web优先的MVP快速验证，4-6周可上线第一版。

三、产品定位与差异化策略

3.1 一句话定位

「多人协作的旅游计划进度看板」—— 让一群人从"去哪玩"到"出发了"的全过程，在一个页面上看得见、改得动、追得到。

3.2 与竞品的核心差异

维度Wanderlog四海轻旅携程AITripTogether（你的）
平台优先级App优先App优先App优先Web优先
核心交互地图拖拽行程地图+笔记转地点AI生成+预订进度看板+地图
协作模式实时共编文档实时编辑+位置共享无协作任务分配+进度追踪+实时共编
规划阶段行程内容行程内容AI生成方案从决策到出发的全流程
进度管理无无无每个环节可标记完成状态
最终交付行程列表行程+游记行程+订单可视化行程单+地图路线
注册门槛需注册需下载App需注册邀请链接免注册查看

3.3 三个差异化抓手

1. 进度看板（独有）

把旅游规划拆成"出发交通→住宿→每日日程→景点间交通→回程交通"等环节，每个环节像一个看板任务卡片，可标记"待规划/规划中/已确认/已完成"。这是市场上没有任何竞品做到的——它们都只关注"行程内容是什么"，而不关注"规划进度到哪了"。

2. Web优先 + 零门槛协作

用户创建计划后生成邀请链接，旅伴点击即可在浏览器中查看完整计划，无需注册/下载。想要编辑时再登录。这极大降低了协作门槛——对比Wanderlog需要所有人下载App+注册。

3. 地图路线总览

所有日程地点在地图上标注，按天用不同颜色连线，直观展示整段旅程的路线。最终生成一份"行程总览图"，可以截图分享到朋友圈。

5.2 数据模型概要

Trip（旅游计划）
  ├─ id, title, destination, start_date, end_date, cover_image
  ├─ owner_id, created_at, status (planning/ongoing/completed)
  ├─ budget_total, currency
  └─ invite_code, share_link

TripMember（计划成员）
  ├─ id, trip_id, user_id, role (owner/editor/viewer)
  └─ joined_at, invited_by

PlanningPhase（规划环节 - 进度看板）
  ├─ id, trip_id, type (departure_transport/accommodation/
  │   daily_schedule/inter_city_transport/return_transport/misc)
  ├─ status (pending/planning/confirmed/completed)
  ├─ assignee_id, due_date
  └─ data (JSON - 根据type存储不同结构)

DailySchedule（每日日程）
  ├─ id, trip_id, date, day_index
  └─ notes, weather_cache

ScheduleItem（日程项）
  ├─ id, schedule_id, type (attraction/food/shopping/rest/activity)
  ├─ title, description, start_time, end_time
  ├─ location_name, latitude, longitude, address
  ├─ status (planned/confirmed/completed), cost
  ├─ sort_order, image_url, notes
  └─ transport_to_next (walk/bus/taxi/subway/drive + detail)

TransportRecord（交通记录）
  ├─ id, trip_id, type (departure/return/inter_city)
  ├─ method (flight/train/bus/car/boat)
  ├─ departure, arrival, dep_time, arr_time
  ├─ cost, booking_ref, status
  └─ notes

Accommodation（住宿记录）
  ├─ id, trip_id, check_in_date, check_out_date
  ├─ name, address, latitude, longitude
  ├─ cost_per_night, total_cost, booking_ref
  ├─ status, room_assignment (JSON)
  └─ notes

Expense（费用记录）
  ├─ id, trip_id, category, amount, currency
  ├─ paid_by_user_id, split_between (JSON)
  └─ description, date

ActivityLog（操作日志）
  ├─ id, trip_id, user_id, action, entity_type
  └─ entity_id, old_value, new_value, timestamp

六、项目实施计划

阶段总览

1

MVP — 核心验证版（第1-4周）

目标：验证"多人协作+进度看板+地图"的核心价值假设

  • 第1周：项目初始化、数据库设计、基础框架搭建、用户认证
  • 第2周：计划创建/邀请/成员管理、进度看板模块、交通/住宿管理
  • 第3周：每日日程模块（增删改查+拖拽排序）、地图标注与连线
  • 第4周：行程总览页面、费用记录、分享链接、联调测试、部署上线

MVP交付物：可在线使用的Web应用，支持创建计划→邀请好友→共同规划→查看进度→地图总览→分享行程

2

V1.1 — 体验优化版（第5-8周）

目标：提升协作体验，补全核心功能闭环

  • 实时协作编辑（WebSocket + 操作广播，非CRDT）
  • 成员权限管理（创建者/编辑者/查看者）
  • 环节负责人指派与截止时间
  • 日程项评论/讨论
  • 操作历史记录与回溯
  • 变更通知（站内消息）
  • 导出PDF行程单
  • AA分账计算
  • 移动端响应式适配优化
3

V2.0 — 协作增强版（第9-14周）

目标：深度协作能力，开始引入商业化探索

  • CRDT实时协作（Yjs集成，真正的多人同编）
  • 地图路线总览图生成与分享
  • 距离/时间预估（接入路线规划API）
  • 日程项图片上传与备注增强
  • 房间分配功能
  • 交通/住宿预订链接接入（携程/美团联盟）
  • 邮件/微信通知推送
  • Pro订阅功能（离线访问、AI行程建议、无限制计划数）
4

V3.0 — 生态扩展版（第15周+）

目标：从工具到平台，探索增长与变现

  • 行程模板市场（用户分享/复用行程模板）
  • AI智能行程规划助手
  • 旅行日记/游记功能
  • 小程序版本
  • 旅行社/企业团建白标方案
  • 多语言支持

七、风险评估与应对

风险等级应对策略
用户迁移成本高（习惯微信群+Excel） 高 邀请链接免注册查看；首次使用引导流程极简化；核心体验必须明显优于DIY方案
Wanderlog进入中国市场 中 Wanderlog目前无中文版/无国内地图；我们以国内地图+微信生态+本地化体验筑墙
大厂（携程/美团）做类似功能 中 大厂聚焦交易闭环，协作规划非其核心路径；我们以轻量、专注、无交易压力的定位差异化
实时协作技术复杂度 中 MVP阶段不引入CRDT，用乐观锁+刷新策略；V2再引入Yjs
地图服务合规性 低 使用腾讯地图/高德地图等持牌服务，确保合规
用户留存率低 中 旅游规划天然低频，但可通过"行程模板复用""历史行程回顾""旅行日记"等功能提升留存

八、下一步行动建议

  1. 立即开始MVP开发——技术可行、市场有空白，4周可验证核心假设
  2. 找到第一批种子用户——身边正在计划出游的朋友/家人（3-5组），用他们的真实场景打磨产品
  3. 关键指标定义——MVP阶段关注：计划创建数、邀请转化率、成员人均编辑次数、计划完成率
  4. 域名与品牌——确定产品名称（TripTogether为暂定名）、注册域名、设计Logo
  5. 合规准备——用户协议/隐私政策、地图服务备案、ICP备案
